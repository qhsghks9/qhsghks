# 솔루션 형태를 정하는 핵심 질문

> 출처: AX컨설팅팀 교육 자료 (2026-10-22 공유) — 원문은 OpenAI 제품 기준. 앞뒤 슬라이드(질문 1의 번호 표기, 질문 4 이후)가 더 있을 수 있음
> 관련: `13_거버넌스_및_운영_맥락.md`, `15_워크플로우_문제에서_사용_사례로.md`, `16_워크플로우_이해를_통한_기회_파악.md`, `24_다음_단계_준비도_점검.md`

사용 사례와 준비도가 확인된 뒤, 솔루션의 형태를 정할 때 묻는 질문들.

## 질문 1: 해당 담당자나 워크플로가 주로 어디에서 운영될 것인가?
- **사용자 또는 제품 인터페이스**(surface)에 관한 질문이다.
- 선택지(원문 기준): **ChatGPT Chat, ChatGPT Work, Codex**, 또는 **API로 구축된 애플리케이션이나 프로세스**

## 질문 2: 어떤 기능이나 아키텍처가 필요한가?
- 여기에는 다음이 포함된다.
  - **비즈니스 맥락**
  - **앱 및 도구**
  - **정보 검색**
  - **구조화된 출력**
  - **코드 실행**
  - **다단계 작업**
  - **일정 관리**
  - **승인 절차**
  - **맞춤형 오케스트레이션**

## 질문 3: 어디서, 어떻게 실행되고 제어될 것인가?
- **배포 및 운영 모델**에 관한 질문이다.
  - **런타임**: 솔루션이 어디서, 어떻게 실행되는지
  - **모니터링과 추적**: 가시성
  - **권한, 승인, 보존, 로깅, 사람의 검토**: 거버넌스 및 운영 통제 수단

## 세 질문의 관계 (참고용 정리)

| 질문 | 다루는 것 | 앞 단계에서 가져올 정보 |
|---|---|---|
| 1. 어디에서 운영되는가 (인터페이스) | 사용자가 AI를 만나는 지점 | 15 문서의 사용자·워크플로우 단계, 10 문서의 워크플로우 흐름 |
| 2. 어떤 기능·아키텍처가 필요한가 | AI가 해야 할 일을 위한 구성 요소 | 16 문서의 AI 지원 유형(검색·추출·생성 등), 24 문서의 데이터·통합 준비 상태 |
| 3. 어디서 어떻게 실행·제어되는가 (배포·운영 모델) | 실행 환경, 가시성, 통제 | 13 문서의 거버넌스 고려 사항, 15 문서의 사람의 역할 |

### 판단 힌트 (참고용 정리 — 일반적 경향이며 고객 상황에 따라 다름)
- **개인·팀이 대화형으로 쓰는 지식 업무**(초안 작성, 요약, 조사) → 기성 채팅/업무용 인터페이스가 빠르다.
- **개발 업무**(코드 작성·리뷰) → 코딩 에이전트 계열 인터페이스.
- **기존 시스템 안에 들어가야 하거나, 대량·자동 처리, 정해진 구조의 출력, 다단계 승인 흐름**이 필요한 경우 → API로 구축한 애플리케이션·프로세스.
- 질문 2의 기능이 많아질수록(코드 실행, 다단계 작업, 일정 관리, 맞춤형 오케스트레이션) 질문 3의 **통제·모니터링 요구도 커진다.**

## 에이전트 모듈에서 다시 정리된 3계층 + 2가지 원칙
> 출처: AX컨설팅팀 교육 자료 (2026-11-04 공유, 에이전트형 AI 모듈)

| 계층 / 원칙 | 설명 |
|---|---|
| **사용자 또는 제품 인터페이스** | 사용자나 워크플로가 주로 어디에서 작동할 것인가? 예: **ChatGPT(Chat 및 Work 포함), Codex**, 또는 **API를 통해 구축된 애플리케이션이나 프로세스** |
| **기능 또는 아키텍처** | 시스템이 무엇을 수행해야 하는가? 예: **워크스페이스 에이전트, 앱 및 도구, 정보 검색, 코드 실행, 단계 간 조정, 자동화** 등 |
| **배포 및 운영** | 작업은 어디에서, 어떤 방식으로 실행되고 제어될 것인가? **신원, 권한, 승인, 보존, 로깅, 수동 검토**, 그리고 작업이 **호스팅되는지 또는 임베드되는지**를 고려한다 |
| **통합 솔루션** | 고객은 **하나 이상의 인터페이스나 기능**을 사용할 수 있지만, **각 계층은 여전히 별도로 평가**되어야 한다 |
| **소프트웨어 제공 워크로드** | 소프트웨어 제공(개발)은 **별도의 인터페이스가 아닌 워크로드**다. 작업이 수행되는 위치와 필요한 기능 및 제어 방식에 따라 **Codex, API 기반 애플리케이션 또는 이들의 조합**을 사용할 수 있다 |

### 이 정리에서 추가된 점 (참고용 정리)
- 배포·운영 계층에 **신원(identity)** 과 **호스팅 vs 임베드**가 명시적으로 추가되었다.
- 기능 계층에 **워크스페이스 에이전트**와 **단계 간 조정**이 들어가 30~33 문서의 에이전트 개념과 연결된다.
- **통합 솔루션** 원칙은 28 문서의 "세 축은 서로 대체할 수 없다"와 같은 이야기다: 인터페이스를 여러 개 쓰더라도 기능·배포 계층을 각각 따로 평가한다.
- **소프트웨어 제공 워크로드** 원칙: "개발 업무 = Codex"처럼 업무 종류를 곧바로 인터페이스로 바꾸지 않는다. 작업 위치·필요 기능·제어 방식을 보고 Codex, API, 또는 조합을 정한다 (위 "판단 힌트"의 개발 업무 항목을 보완).

## Codex vs ChatGPT vs OpenAI API 위치 비교
> 출처: AX컨설팅팀 교육 자료 (2026-11-04 공유). "이 비교표를 활용하여 Codex가 ChatGPT 및 OpenAI API와 비교하여 어떤 위치에 있는지 빠르게 파악해 보세요."

```
┌──────────────┐   ┌──────────────┐   ┌────────────────────┐
│   ChatGPT    │   │  OpenAI API  │   │       Codex        │
│              │   │              │   │                    │
│ Chat         │   │ Embedded +   │   │ Software delivery  │
│  Collaborate │   │ custom AI    │   │ work               │
│ ──────────── │   │              │   │ · ChatGPT desktop  │
│ Work         │   │              │   │ · Codex CLI        │
│  Delegate    │   │      ▲       │   │ · IDE extension    │
│              │   │      │       │   │ · Codex cloud      │
│              │   │      │       │   │ · GitHub workflows │
└──────────────┘   └──────┼───────┘   └─────────┬──────────┘
                          └── Build + Maintain ─┘
```

| 제품 | 역할 | 의미 |
|---|---|---|
| **ChatGPT – Chat** | **Collaborate** (협업) | 사람이 AI와 대화하며 함께 작업 |
| **ChatGPT – Work** | **Delegate** (위임) | 업무를 AI에 맡겨 처리 (워크스페이스 에이전트 등) |
| **OpenAI API** | **Embedded + custom AI** (임베드·맞춤형 AI) | 고객의 제품·시스템·프로세스 안에 AI를 넣어 구축 |
| **Codex** | **Software delivery work** (소프트웨어 제공 업무) | 사용 경로: ChatGPT 데스크톱 앱, Codex CLI, IDE 확장, Codex cloud, GitHub 워크플로 |
| **Codex → API** | **Build + Maintain** | Codex로 API 기반 애플리케이션을 **구축하고 유지보수** |

### 읽는 법 (참고용 정리)
- ChatGPT는 **사람이 쓰는 업무 인터페이스**(협업 → 위임), API는 **고객 시스템에 내장되는 AI**, Codex는 **소프트웨어를 만드는 일**에 쓰인다.
- **Build + Maintain** 화살표: Codex와 API는 경쟁 관계가 아니라 **Codex로 API 기반 애플리케이션을 만들고 유지보수**하는 관계다. 위 "소프트웨어 제공 워크로드" 원칙(Codex, API, 또는 조합)과 같은 이야기다.
- Codex는 하나의 앱이 아니라 **여러 접점**(데스크톱, CLI, IDE, 클라우드, GitHub)에서 쓰인다. 개발자가 이미 일하는 곳에 맞춰 제안한다.
- 고객 요구를 빠르게 분류하는 질문:
  - "직원들이 AI와 함께/AI에게 맡겨 일하려는 건가?" → ChatGPT (Chat / Work)
  - "우리 제품·시스템 안에 AI를 넣으려는 건가?" → API
  - "소프트웨어를 더 빨리 만들고 유지보수하려는 건가?" → Codex (그리고 그 결과물이 API 앱일 수 있음)

## 방향성을 제안하기 전에 확인할 상충 관계(트레이드오프)
방향성을 제안하기 전에, 어떤 상충 관계가 경로를 **더 강화하거나, 약화시키거나, 시기상조로 만들거나, 다른 팀과의 인계에 의존하게** 만드는지 확인한다.

| 상충 관계 | 판매자 질문 | 영향을 미칠 수 있는 사항 |
|---|---|---|
| **비용** | 구축, 운영, 관리 또는 확장에 많은 비용이 들까요? | 해당 가치 제안이 해당 방식을 채택할 만큼 충분히 설득력이 있는가? |
| **지연 시간** | 워크플로우에 실시간 또는 준실시간 응답이 필요한가? | 라우팅 전에 기술적 검증이 필요한지 여부 |
| **통합** | 해당 솔루션에 앱, 도구, 시스템 통합 또는 임베디드 경험이 필요한가요? | API 기반 애플리케이션, Workspace Agent, 앱 액션, 결합된 솔루션 또는 기술적 인계에 대한 검증이 필요한지 여부 |
| **데이터** | 어떤 데이터가 필요하며, 어디에 저장되어 있고, 그 민감도는 어느 정도인가요? | 접근, 거버넌스, 보안, 사용 가능한 호스팅형 제어 수단 또는 자체 관리형 오픈-웨이트 요구 사항 중 어떤 부분에 대한 검증이 필요한지 확인 |
| **거버넌스** | 어떤 승인, 정책, 감사 필요 사항 또는 감독 요건이 적용됩니까? | 검증 세션이 필요한지, 아니면 배포 인계가 필요한지 여부 |
| **도입** | 누가 이 솔루션을 사용해야 하며, 어떤 행동이 바뀌어야 합니까? | 해당 솔루션이 실제로 가치를 창출할 준비가 되어 있는지 여부 |
| **복잡성** | 제안된 접근 방식이 성숙도, 시급성 및 기대 가치에 비례하는가? | 해당 방안을 단순화하거나 단계적으로 진행해야 하는지 여부 |
| **사람의 역할과 되돌릴 수 있는 여부** | 사람이 결과물을 검토, 승인, 무시 또는 감독해야 합니까? 실수는 쉽게 수정할 수 있습니까? | 승인, 감사, 에스컬레이션 또는 검토 통제에 대한 검증이 필요한지 여부 |

*(마지막 행은 이미지 하단이 일부 잘려 있어 보이는 범위까지 기록. 아래에 행이 더 있을 수 있음)*

### 상충 관계 읽는 법 (참고용 정리)
- 각 상충 관계는 경로를 **강화**(예: 데이터가 잘 준비됨) / **약화**(예: 비용 대비 가치가 약함) / **시기상조**(예: 도입·거버넌스 준비 부족) / **다른 팀 인계 필요**(예: 실시간 지연·통합·자체 호스팅 → 기술팀 검증) 중 하나로 작용한다.
- "영향을 미칠 수 있는 사항" 칸의 대부분이 **"~에 대한 검증이 필요한지 여부"** 다. 즉 판매자가 이 자리에서 결론을 내기보다, **무엇을 누구에게 검증받아야 하는지**를 가려내는 것이 목적이다.
- **복잡성**은 12 문서의 AI 성숙도, 17 문서의 범위 및 복잡성과 연결된다: 성숙도·시급성에 비해 과한 설계라면 **단순화하거나 단계적으로** 제안한다.
- **사람의 역할과 되돌릴 수 있는 여부**는 15 문서의 사람의 역할, 17 문서의 위험 및 통제와 같은 축이다. 실수를 되돌리기 어려운 업무일수록 승인·감사 통제 검증이 먼저다.
- 원문의 **Workspace Agent, 앱 액션, 자체 관리형 오픈-웨이트(open-weight) 모델** 등은 OpenAI 제품·배포 옵션 기준 용어다.

## 컨설팅 적용
- 세 질문은 **사용 사례가 정의된 후**에 다룬다. 고객이 처음부터 "ChatGPT를 쓸까요, API를 쓸까요?"로 시작하면 09 문서의 방향 전환 질문으로 워크플로우 문제부터 확인한다.
- 질문 3은 13 문서의 거버넌스 항목(데이터 민감도, 승인, 규정 준수, 인적 검토, 모니터링, 내부 정책)과 함께 **CIO/CTO·보안 담당자**(22 문서 강조점)와 논의한다.
- 원문은 OpenAI 제품 기준이다. 다른 AI 벤더 제품을 제안할 때도 **인터페이스 → 기능/아키텍처 → 런타임/통제** 3단계 질문 구조는 그대로 쓸 수 있다.
