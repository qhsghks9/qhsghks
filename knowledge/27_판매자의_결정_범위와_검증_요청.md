# 판매자의 결정 범위와 검증 요청 기준

## 다음 사항에 대해서는 결정해서는 안 된다
- **법적 또는 규제적 해석**
- **보안 아키텍처** 또는 **규정 준수 승인**
- **API 설계, SDK 사용, 모델 평가, 배포 구성** 또는 **운영 아키텍처**
- **개방형(오픈-웨이트) 모델 인프라, 자체 관리 운영, 데이터 상주 구현** 또는 **에어갭(air-gapped) 배포 설계**
- **마이그레이션 계획 세부 사항** 또는 **프로덕션 배포 절차**

## 다음과 같은 경우에는 진행하기 전에 검증을 요청해야 한다
- **데이터 경계가 불분명**한 경우
- 고객이 **기술 아키텍처 관련 결정**을 요구하는 경우
- 고객사가 **중요한 업무, 규제 대상 또는 극도로 민감한 워크플로우**를 보유하고 있는 경우
- 고객이 **기존 AI 솔루션이나 벤더 의존형 워크플로우를 교체**하는 경우
- 권장 사항이 **오픈 웨이트 모델, 마이그레이션, 고급 에이전트 기능**, 또는 **인터페이스·기능·운영 모델의 조합**에 의존하는 경우

## 정리: 판매자(컨설턴트)의 역할 경계 (참고용 정리)

| 판매자가 하는 일 | 판매자가 하지 않는 일 (전문가에게 검증 요청) |
|---|---|
| 워크플로우 문제·증거·이해관계자 파악 | 법·규제 해석 |
| 사용 사례와 가치 가설 정리 | 보안 아키텍처 설계, 규정 준수 승인 |
| 예상 표면(인터페이스)과 대안의 방향성 제시 (25 문서) | API·SDK·배포·운영 아키텍처 결정, 모델 평가 |
| 거버넌스·데이터 고려 사항을 **식별** (13 문서) | 오픈-웨이트·자체 운영·데이터 상주·에어갭 설계 |
| 위험·가정·미해결 사항을 **기록**하고 인계 (26 문서) | 마이그레이션 세부 계획, 프로덕션 배포 절차 |

> 13 문서의 원칙("통제 수단을 설계하는 것이 아니라 진행 여부에 영향을 미칠 수 있는지 파악하는 것")과 같은 맥락이다. 판매자는 **고려 사항을 발견하고 넘기는 사람**이지, **결정하는 사람**이 아니다.

## 검증 요청 조건과 관련 문서 (참고용 정리)

| 검증 요청 조건 | 관련 문서 |
|---|---|
| 데이터 경계가 불분명 | 13 (데이터 민감도), 25 (상충 관계: 데이터) |
| 고객이 기술 아키텍처 결정을 요구 | 25 (질문 2·3) |
| 중요·규제 대상·극도로 민감한 워크플로우 | 08 (경계가 모호한 민감한 워크플로우), 13 |
| 기존 AI·벤더 의존 워크플로우 교체 | 23 (기존 AI 대체 → 마이그레이션 현황 파악) |
| 오픈 웨이트·마이그레이션·고급 에이전트·조합형 권장 | 25 (상충 관계: 통합·복잡성) |

## 컨설팅 적용
- 고객이 "이거 규정상 괜찮죠?", "어떤 아키텍처로 가면 되나요?"라고 물으면 **즉답하지 않는다.** "중요한 질문이라 해당 전문가(법무·보안·기술팀) 검증을 받아 정확히 답드리겠습니다"라고 하고, 질문을 26 문서 인계 항목의 **위험·가정·미해결 사항**에 기록한다.
- 즉답을 피하는 것은 회피가 아니라 **신뢰를 지키는 것**이다. 잘못된 확언은 이후 검증 단계에서 기회 전체의 신뢰를 무너뜨린다.
- 위 검증 요청 조건 중 하나라도 해당하면, 다음 단계 계획에 **기술·보안·법무 검증 세션**을 포함하고 담당자를 지정한다.
- 원문의 "판매자"는 파트너사 영업/컨설턴트를 의미하며, AX 컨설턴트에게도 동일하게 적용된다.
